# LLM Relay 开发阶段与验收标准

第一版明确包含对外服务与客户计费。以下阶段是同一商业版本的内部开发顺序，只有全部完成才能宣布可对外收费。当前只完成规划，应用、支付和网关均尚未实施。

## 阶段 0 项目与租户基础

建立 Go gateway、Next.js/HeroUI 客户控制台与运营后台、MySQL/Redis Compose、配置样例和 CI。核对受支持依赖版本，使用 mock 上游开展开发。

从第一份 schema 开始纳入 Tenant、Membership、Project、AccessKey、PriceVersion、CustomerWallet、WalletHold、不可变资金账本及支付订单；上游 BudgetAccount 保持独立。加入客户注册登录、项目权限、运营角色和审计。

验收：两个租户、多个项目与访问 Key 的权限相互隔离；客户不能访问运营 API、采购价、上游 Key 或其他租户数据；Key 轮换不改变项目资源所有权。

## 阶段 1 原生转发与代理

交付官方/兼容 Endpoint、多 Key 配置、SOCKS5、Claude Messages 与 OpenAI Chat Completions/Responses 的 JSON/SSE。该阶段仅供开发验证；Responses 资源归属完成前只开放明确的无状态模式，不能对外宣称完整商业服务。

验收：

- 两种协议的官方与兼容 mock 上游可用，路径前缀不重复或覆盖 host。
- 认证只发送给绑定上游，客户端不能指定任意 URL 或伪造上游组织/项目。
- 流式事件、工具调用和未知字段保留；首事件及时输出，取消中断上游。
- SOCKS5 可认证，失败不直连；上游重定向不泄漏 Key，日志无秘密。
- 不支持的端点、资源引用和无法计量的能力明确拒绝。

## 阶段 2 调度、钱包和双账结算

交付共享限流组、三种路由策略、租户/Key/上游组 RPM/TPM/并发限制、冷却与熔断、客户销售价快照、钱包预留结算、上游成本分账、Responses 归属与请求幂等扩展。

验收：

- 20 个并发请求竞争 5 个剩余槽位时最多放行 5 个；多个上游 Key 共享同一组容量。
- 客户创建更多访问 Key 不能突破租户限额；单租户不能占满全部等待队列。
- 额度优先只比较同口径、未过期的上游余额；未知余额只能进入显式备用路线。
- 官方专用路由组不落到第三方；能力不符的模型不静默降级。
- 钱包不足在调用前拒绝；两个实例同时预留不会透支已知余额。
- MySQL 预留成功但 Redis 抢占失败能补偿；发送前后崩溃恢复不重复扣款或无条件退款。
- 跨预算周期完成结算到原期间，重置不删除未完成预留；恢复不与活跃请求竞态退款。
- 客户每个逻辑请求最多一张消费单；各 attempt 都入成本账，平台重试不重复向客户收费。
- 客户价格在请求期间改变或后台切换 Key，已受理请求仍按原销售价快照结算。
- 重复完成通知只结算一次，缓存和累计 usage 不重复计价，小额计量符合固定精度规则。
- 平台失败、客户取消、缺 usage 分别按收费政策处理；待核对超时释放客户预留，晚到成本不静默追扣客户。
- SSE 中途失败不换 Key 重放；同幂等键并发提交只执行一次，同键不同请求冲突。
- Responses 跨租户或跨项目引用被拒绝；同项目访问 Key 轮换后可续接原资源；不随机跨上游路由。
- response ID 对外可见前归属已落库；写入失败不暴露该 ID。
- Redis/资金数据库故障停止接纳新的收费请求，已有流保留可恢复的状态证据。

## 阶段 3 充值、退款和支付对账

交付一个适用的在线收款渠道、充值订单、验签通知收件箱、幂等到账、退款状态机、拒付处理、审计补款、资金批次分摊与对账。支付渠道接入前确定商户主体、目标地区、币种和充值档位。

验收：

- 伪造成功跳转、无效签名、金额/币种/租户或测试模式不匹配均不能增加余额。
- 未完成付款及异步支付尚未成功时不入账；支付成功仅入账一次。
- 重复事件、不同事件指向同笔付款、乱序事件均不重复充值。
- 事件已保存但处理崩溃可恢复；未完成事件不能仅因 ID 存在而丢弃。
- 创建支付或退款网络结果不明时查询原对象，不能重复发起业务动作。
- 退款与请求预留并发时不双花；pending 保持冻结，成功冲销、失败释放，退款归属原支付批次。
- 赠金不能退现金；累计退款、在途退款及拒付不会形成重复补偿。
- 已消费后发生拒付可记录欠款并停用新请求；赢得争议后的恢复只执行一次。
- 支付成功但漏通知可以主动对账补记；订单、资金账本、请求费用和持有预留可核对。

## 阶段 4 客户闭环与上线验收

客户界面包含注册登录、项目与成员、API Key、模型及价格、SDK 接入、钱包、充值、付款记录、消费账单与导出。运营后台包含客户、价格、上游、代理、路由、订单、退款/拒付、补款、成本统计与对账差异。

验收：

- 新客户注册→充值→创建项目和 API Key→调用 Claude/OpenAI→查看费用与余额的闭环完整。
- 客户能看到成交单价、计量依据、预留/待核对原因和释放时限；客户界面不泄漏上游秘密及采购价。
- 运营能解释选路原因，分别查看客户收费和全部上游成本，不能把充值额当模型消费额。
- 账单与导出按租户权限保护；退款、调账、改价和封禁都有审计记录。
- 表单、空状态、加载、错误、删除确认、键盘、桌面和移动视图完成验证。
- 网关滚动更新可排空进行中的 SSE，入口无流缓冲，连接及流超时经过验证。
- 完成真实供应商和指定代理的最小烟测，以及选定支付渠道的测试环境闭环；真实收款配置启用前核对生效价格及支付配置。

## 后续阶段

包月额度、订阅折扣、自动充值、企业后付费、优惠活动、多币种自动换汇和更多支付渠道后置。供应商余额插件、Admin Usage/Cost 对账、自动限额同步、更多资源 API、Realtime/WebSocket 和跨协议转换按需求扩展。

## 默认与待配置项

| 项目 | 当前方案 |
| --- | --- |
| 项目名 | LLM Relay / `llm-relay`，可更名 |
| 使用范围 | 对外多租户服务，客户计费在一期 |
| 商业模式 | 建议预充值按量扣费，余额不足拒绝新调用 |
| 销售价 | 模型价目表＋客户专属价，请求固定版本 |
| 路由 | 负载优先，可选额度优先或均衡；限制在客户允许的路由组 |
| 钱包与成本 | MySQL 持久双账；客户余额、上游余额、内部预算独立 |
| 支付 | 适配层＋首个适用渠道；具体商户/地区/渠道尚未指定 |
| 币种 | 建议首期 USD 单币种，收款接入时确定 |
| ss5 | SOCKS5，出口失败不直连 |
| 预算周期 | 保存时区，默认 Asia/Singapore |
| 待核对期限 | 建议 24 小时，政策版本化并向客户公开 |
| 部署 | 开发 Docker Compose，生产接现有 TKE 流程 |

未确定的销售单价、收款主体与支付渠道是启用真实收费所需输入，不阻止核心开发。真实上游 Key 和支付密钥通过后台或部署 Secret 注入，禁止写入仓库。
