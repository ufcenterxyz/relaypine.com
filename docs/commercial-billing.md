# LLM Relay 客户与商业计费规格

第一版面向外部客户提供 Claude、OpenAI API 中转。建议商业模式为预充值后按模型用量扣费；租户隔离、客户控制台、充值、钱包、价目表、消费账单、退款和运营对账均为一期范围。本文是实现规格，尚未接入真实收款。

## 1. 客户及权限

`Tenant` 是计费和数据隔离单位。用户通过 Membership 加入租户；一期提供 owner、developer、billing viewer 三类角色，运营人员采用独立角色。owner 管理充值、成员和访问 Key；developer 管理其获准项目的 Key 与请求；billing viewer 只读账单，不获得推理凭据。内部业务也可作为一个租户使用相同入口。

访问 Key 哈希在服务端解析为 tenant_id 和 project_id，不能信任请求参数中的归属。数据库查询、缓存、限流、异步任务、导出、幂等键及 Responses 归属都必须包含并验证租户和项目作用域。资源归属为租户/项目，访问 Key 只是可轮换的凭据；同项目的新 Key 在获得相应权限后可续接原资源，跨项目默认拒绝。后台仍保留创建时的 Key ID 用于审计。

客户可选其获准的模型、服务等级和路由组。路由组定义官方专用或允许兼容服务等供应商范围；运行时只能在客户购买的范围内切换。客户不能指定平台私有上游 Key、任意 host 或代理。

客户总 RPM/TPM/并发和访问 Key 子限额同时生效。短等待队列按租户限额和公平性管理，防止单个客户耗尽所有可用连接。

## 2. 价格与成本分离

维护两套独立数据：

| 数据 | 计量维度 | 用途 |
| --- | --- | --- |
| 上游成本 | 每个 attempt，按实际供应商及采购价格版本 | 预算控制、对账、成本统计 |
| 客户费用 | 每个逻辑 request，按销售价格快照和可计费用量 | 扣减客户钱包、客户账单 |

销售价按模型分别配置输入、输出、缓存读取、缓存写入等适用费率，以每百万 token 表示。计量适配器保证不同 token 类别不会重复计价；无法精确计量的能力在商业入口禁用。客户专属价覆盖公开价；倍数定价可用于生成销售价，但请求执行时锁定具体费率，不能随一次换 Key 改变。

PriceVersion 只新增，不修改历史版本。请求锁定 `price_version`、币种、计量规则版本和客户收费政策；跨日、改价和重试都保持原快照。模型别名只有能力相符且用户获准的映射才能选路；不得静默降级到更便宜但不等价的模型。

一期单一结算币种建议 USD，实际支付渠道和收款币种在接入时依据收款主体、目标客户地区与已有渠道确定。模型费用内部使用高精度整数或定点计量，充值按支付渠道最小货币单位转换；小额请求的精度和舍入规则固定，不逐 token 舍入。不同币种不得直接相减或比较利润，第一版不自动换汇。

报表将客户消费额、全部上游尝试成本、折扣/赠送、退款、支付手续费分开列示。充值记录表示客户已支付的预付金额，不直接当作模型消费额；费用未核对时单列待核对成本，不输出虚假精确的毛差。

## 3. 客户钱包与不可变账本

客户付费余额、赠送余额、可用余额、冻结和请求预留分别记录。赠送额度用于管理员审计后的补偿或试用，不可作为现金退款；消费记录分摊资金来源，以便撤销消费时返还到原来源。第一版不提供余额转账、提现或自动信用透支。

资金操作写入不可变 LedgerTransaction/Entry；采用同币种配平的资金分录，每笔有业务原因、操作者、源订单/请求和唯一业务键。余额是账本的事务投影，不能靠直接修改 balance 字段调账；纠错使用反向分录。管理员人工补款必须记录付款凭证或调整原因，不能伪造支付成功事件。

`可用余额 = 账面可消费余额 - 活跃请求预留 - 退款/风险冻结`。预留是可用性约束，最终扣费才形成消费分录；不能同时把预留和结算扣两次余额。余额校验、预留、消费/释放、幂等状态在同一 MySQL 事务中更新。请求日/月上限是钱包之外的消费控制，不能代替钱包。

## 4. 请求预留与收费政策

客户请求只建立一份 WalletHold 和最多一张 CustomerCharge。选路后的每个上游 attempt 另有成本预留，内部切换 Key 不再创建客户预留或客户账单。

商业入口在发往上游前按销售价预留可信最大成本，必须有输出上限和适用的输入计量上界；余额不足在调用前拒绝。对于难以确定上界的功能，一期明确拒绝或使用已验证的保守上界。若实际费用超出本次已告知并预留的上限，默认客户收费封顶，差额记平台成本异常，不能事后擅自透支。

客户预留与选定上游成本预留可在同一 MySQL 事务按固定锁顺序完成，再获取 Redis 容量。候选路线抢占失败时，只释放该 attempt 尚未发送的上游成本预留；继续选路和换 Key 期间保留同一客户 WalletHold，逐次处理上游成本预留。请求最终无法执行、取消或终结时，再按下述收费政策结算或释放客户预留。选路等待仍受短队列时限约束。

默认收费政策如下，需在客户价格与接入说明中公开：

| 请求结果 | 客户侧 | 平台上游侧 |
| --- | --- | --- |
| 鉴权、模型权限、限流或余额不足，在发送前拒绝 | 不收费 | 无推理成本 |
| 成功且有可信 usage | 按锁定售价和实际计量结算一笔 | 记录所有 attempt 的实际成本 |
| 平台内部重试后成功 | 仅按最终成功尝试结算一笔 | 失败尝试成本由平台承担 |
| 平台/上游错误导致失败或中断 | 默认不向客户收费，释放客户预留 | 已发生或未知成本仍记录并核对 |
| 客户主动取消或断开，已有可信计量 | 按本次已确认的可计费用量结算，最高不超过预留 | 按实际或待核对成本记录 |
| 成功或客户取消，但缺少可信 usage | 客户侧显示待核对，暂不按猜测扣费 | 保留待核对成本 |

首版建议待核对上限为 24 小时：期限内拿到可信的请求级计量才结算；超时释放客户预留并终结为不收费，未核对成本由平台继续跟踪。终结后晚到的数据仅调整平台成本，不静默追扣客户。该期限是可配置的产品政策，需版本化；客户可见冻结原因和释放时限。重复取消/无 usage 触发行为限流或审查，不能通过无限预留规避可用余额控制。

若无法可靠区分客户端断连与平台断流，采用对客户有利的失败处理并记录诊断原因。对所有异常保持上游成本与客户费用分开，不将“客户免费”误写为“上游没有收费”。

幂等结算保证同一 request_id 只收费一次。另提供网关幂等键，唯一作用域为租户、项目、端点和幂等键，另存规范请求摘要用于比较；同键不同请求返回冲突，相同进行中或完成的请求不再次调用。第一版不保存完整正文用于 SSE 重放；重复提交返回协议可识别的冲突/状态信息与原 request_id，客户端另查用量状态。此行为是显式启用的网关扩展，不伪装成原生生成响应。未提供幂等键而重新发起的请求按新请求处理，并在接入文档说明。去重记录建议保留 24 小时，期限向客户端公开，客户费用账本的唯一性约束永久保留。

## 5. 充值与支付

支付采用适配层；Stripe Checkout 可作为候选，但此阶段不预设用户已有可用商户账户，也不把订阅模板直接用于单次充值。一期交付一个适用的在线支付渠道，并提供带审计的人工补款。包月订阅、自动续费和自动充值后置。

服务端创建 TopUpOrder，锁定 tenant、金额、币种和赠送规则；客户端只能选择服务端支持的档位/金额，不决定入账结果。订单与支付对象唯一关联。用户跳回成功页面只展示查询结果，不直接增加余额。

支付通知校验签名和原始请求体，验证支付账户、测试/正式模式、订单归属、金额、币种、支付对象及成功状态；成功充值只入账一次。若使用 Stripe，异步支付需要等待真正付款成功，不能仅凭 Checkout 完成就发放余额。[Stripe Checkout 履约](https://docs.stripe.com/checkout/fulfillment?payment-ui=stripe-hosted)

通知采用持久收件箱：验签后保存事件再确认接收；处理任务可重试，只有钱包入账事务成功才标记处理完成。不能因为 event ID 已存在就把未处理成功的事件跳过。除 event ID 去重，还按 payment/order 的业务键约束入账，阻止不同事件重复增加余额。乱序通知通过当前支付状态与允许的状态迁移处理，定期主动查询补漏。[Stripe Webhook 行为](https://docs.stripe.com/webhooks)

创建支付、退款调用使用稳定幂等键；网络结果不明先查询原支付对象，不能盲目创建第二笔。支付渠道的结算手续费不影响已承诺给客户的充值额度，除非价格页面明确约定。

## 6. 退款、拒付与对账

退款是一条独立状态机。每次充值形成关联原支付的资金批次，预留、消费和退款都记录批次分摊，避免退款到无关支付。管理员只能对可退的已付额度发起，累计成功或在途退款不超过原支付金额，并扣除已消费、已预留、赠送和此前退款对应部分。事务中先冻结对应可退余额，再向原支付调用退款；请求受理不等于成功，成功后结算冻结，失败后释放冻结。结果未知时继续冻结并查询，不能提前恢复为可消费余额。Stripe 退款有 pending/failed 状态，需要按最终状态处理。[Stripe 退款](https://docs.stripe.com/refunds)

拒付单独记录并暂停相关租户新消费，保留进行中请求及账本证据；支付撤销可能在余额已消费后造成欠款，记录独立应收/亏损状态，不改写历史账单或伪造余额。退款和拒付共用原支付的累计补偿约束，不能重复返还同一笔资金；有在途退款时查询并核对支付平台最终结果。争议撤回或赢得后仅通过幂等冲正恢复对应资金/冻结状态，不能重复充值。实际退款和解冻必须由获准角色操作并审计。

每日做支付订单与到账、到账与钱包分录、请求费用与钱包扣款、预留与请求终态的核对。提供可重跑的恢复任务、差异列表和人工处理入口。客户用量账单与付款收据分别展示；法定发票及税额字段由确定的收款主体和支付渠道提供，不把普通用量导出标记为税务发票。

## 7. 一期界面与完成条件

客户侧：注册登录、账户与成员、API Key、模型与价格、接入示例、余额与预留、充值、付款记录、消费明细和导出、余额不足与请求异常提示。

运营侧：客户与权限、客户总限额、上游池与代理、模型价目与专属价、充值订单、退款和拒付、补款及补偿、成本与消费额、对账差异、审计日志。

第一版上线前必须完成真实支付渠道的测试环境闭环和两个租户的隔离验收。实际收费价格、收款主体、支付渠道和币种在启用真实收款前落实；这些是运营配置与验收输入，不影响当前的数据模型和核心网关开发。
