# RelayPine HTTP contract

Console uses same-origin `/api/*`, proxied to Go. `APP_URL` is the customer origin and `ADMIN_APP_URL` is a distinct administrative hostname. Production requires HTTPS for both. The gateway matches the HTTP Host directly and ignores `X-Forwarded-Host`; unknown hosts cannot access console APIs. JSON mutations require the exact Origin of the requested surface. Errors: `{ "error": { "code": "...", "message": "..." } }`.

- GET `/api/auth/config` -> `{surface:"customer"|"admin",app_url,admin_app_url}` without authentication. This contains no administrator identity or private configuration.
- POST `/api/auth/code` `{email,name?}` -> HTTP 202 `{status:"code_sent",expires_in:600,resend_after:60}`. A cryptographically random six-digit code is emailed to the normalized address. Names are optional (up to 100 UTF-8 bytes) and bound to that challenge. Sending creates no account or session.
- POST `/api/auth/verify` `{email,code}` -> HTTP 200 `{status:"authenticated",user,surface,app_url,admin_app_url}` and a host-only HttpOnly SameSite=Lax session cookie. On the customer origin, any verified active email can sign in; first sign-in provisions a separate tenant, default project and zero-balance wallet, with no automatic credit or API key. On the administrative origin, only the configured `SUPERADMIN_EMAIL` with a durable operator role can receive a session; other verified addresses receive 403 `forbidden`. Administrative privileges are never exposed by a customer-origin session, including the superadmin's session.
- Codes expire after ten minutes, allow at most five wrong attempts, are single-use and bound to the requesting surface. Resending invalidates the previous code. Verification consumes the challenge atomically. A code issued at the customer origin cannot authenticate on the admin origin. Sessions also persist their surface audience; copying a valid cookie across hosts does not authenticate it there.
- Code delivery has a 60-second resend cooldown and ten-send limit per email per hour, shared across surfaces. Both endpoints additionally enforce normalized-email, IP and email/IP-pair rate limits. HTTP 429 includes `Retry-After` and `error.retry_after` seconds; code errors are `invalid_code`/`expired_code`. Delivery not configured or rejected returns 503 `email_unavailable`; storage failures return 503 `auth_unavailable` or fail-closed 429 from the limiter. Codes are never exposed in API responses or logs.
- Former POST `/api/auth/login`, `/api/auth/register`, and `/api/waitlist` return HTTP 410 `verification_required`. They cannot authenticate passwords or bypass mailbox verification.
- POST `/api/auth/logout` -> `{ok:true}`; expires only the current surface's session.
- GET `/api/auth/me` -> `{user,surface,app_url,admin_app_url}`; unauthenticated 401.
- GET `/api/state` -> Snapshot from `services/gateway/internal/domain/types.go` plus `surface`, `app_url`, `admin_app_url`; unauthenticated 401. Customer snapshots contain only the session tenant's wallet, keys, requests and ledger, plus enabled published models with selling rates. They omit upstream names, procurement prices/reference metadata, credentials, endpoints, proxies, other customers, and internal routing strategy. `user.operator` is false on the customer surface. Administrative snapshots include operational configuration and cross-tenant request visibility. Legacy `waitlist` remains an empty array for response compatibility. Money is micro-USD; rates are micro-USD per million tokens.
- All `/api/admin/*` routes require the admin hostname, a surface-bound admin session, exact admin Origin, and POST. Requests to those routes on the customer hostname return 404, regardless of account role. Customer accounts cannot mint an admin session.
- GET `/api/requests/{id}` -> `{request,payload?,retention_days}`; unauthenticated 401, unknown or other-tenant IDs 404. `request` uses the snapshot request shape. `payload` holds the captured exchange: `request {method,path,headers,body,bytes,truncated?}` with the client's original body before model aliasing and output-limit normalization, and only `content-type`, `user-agent`, `anthropic-version` and `anthropic-beta` headers; `response {status,content_type,body,bytes,truncated?}` is exactly what the client received, including SSE frames. Bodies are strings; at most 4 MiB of a response is kept and `bytes` is the full size. `upstream` is the provider reply the client did not receive, such as an upstream error (64 KiB kept); it appears only on the administrator surface. Customers can read only their own tenant's requests; the administrator can read any. `payload` is absent while a request runs, when capture is off (`retention_days` 0), after the retention window, and for requests made before capture. Bodies are gzip-compressed and sealed with `MASTER_KEY` (AES-GCM bound to the request ID) and pruned after `REQUEST_BODY_RETENTION_DAYS` (default 7).
- POST `/api/keys` `{name,models:[],rpm:60}` -> `{key,secret}` secret displayed once.
- DELETE `/api/keys/{id}` revokes tenant-owned key.
- POST `/api/admin/endpoints` full Endpoint fields; no ID creates, with ID updates.
- POST `/api/admin/credentials` full Credential fields plus `secret` on create/rotation. Empty secret preserves existing. Optional `workspace_id` is trimmed and must match `wrkspc_[A-Za-z0-9]+` within 128 ASCII characters, or be empty. A nonempty workspace is allowed only for an Anthropic endpoint. The value is returned in the administrator snapshot; raw upstream secrets are never returned.
- Creating a credential may submit only `{endpoint_id,secret}`. Omitted advanced settings receive local defaults: generated name, endpoint-shared quota group, RPM 60, TPM 100000, concurrency 10, enabled true, budget and priority 0. Explicit invalid zero capacities are rejected; explicit overrides, including enabled false, are preserved. Updates retain full-object semantics.
- POST `/api/admin/credentials/discover` `{id?,endpoint_id,secret?,workspace_id?,proxy_id?}` performs bounded read-only upstream discovery. Blank secret may reuse exactly the supplied credential ID on the same endpoint; no stored secret is returned. Saved proxy selection is honored with no direct fallback. Response: `{status:"verified"|"workspace_required",models:[{id,name,max_output_tokens?}],workspaces:[{id,name}],workspace_id,organization_id,defaults,limits_source:"provider"|"default",warnings,checked_at}`. Discovery does not save credentials/models or generate billable inference. Requires the configured superadmin session, same-origin POST, and rate-limit allowance.
- POST `/api/admin/proxies` `{id?,name,url,enabled}`; empty URL preserves existing.
- POST `/api/admin/models` full Model fields; save increments version. Optional `create_only:true` performs an atomic insert and returns 409 if the ID exists. Enabled models require `billing_mode=metered` and positive input/output sales and cost rates; incomplete models can only be saved disabled. Client-supplied `pricing_reference` claims are never trusted. Unchanged rates preserve the stored reference policy; changed rates clear it. Optional `manual_pricing:true` explicitly clears reference pricing and its official-host restriction even when the numeric rates are unchanged. Status-only toggles should omit this flag.
- POST `/api/admin/models/prices/preview` with `{model_ids?:string[]}` previews existing models (omitting IDs means all, maximum 400). For import use `{credential_id,models:[Model,...]}` instead. The gateway fetches the current official public standard-text price tables without sending upstream credentials. Import prices submitted by the client are ignored. A source outage or changed table returns 503 without changing data. Response: `{preview_id,kind:"update"|"import",checked_at,expires_at,sources:[{provider,url,checked_at,error?}],items:[{id,name,version,status:"matched"|"manual"|"unmatched",reason?,before:Model,after:Model,source_url?,source_name?,reference_model?}]}`. A matched row has reference sell/cost rates at 1:1 and `billing_mode=metered`; disabled existing models stay disabled. Differing manual rates are marked for explicit opt-in overwrite. Unknown unpriced models become disabled drafts with `pricing_note`. Existing manually priced unmatched models are preserved.
- POST `/api/admin/models/prices/apply` `{preview_id,model_ids:[...]}` applies selected existing-model changes from a server-held 15-minute preview. One transaction locks and validates every expected version; any concurrent edit returns 409 and rolls the whole batch back. It updates rates/reference metadata and can disable unpriced models; it does not edit aliases, output caps, balances, or historical price snapshots. Response: `{updated_count,results:[{id,status:"updated"}]}`. After an uncertain response, refresh current models rather than assuming failure.
- POST `/api/admin/models/import` `{preview_id,model_ids:[...]}` imports selected rows from an import preview. Explicit manual configuration clients can instead submit `{models:[Model,...]}` with complete metered prices or disabled drafts; they cannot assert reference metadata or publish usage-only models. Both forms accept 1–400 models and are always create-only. Duplicate submitted IDs are rejected; existing catalog IDs are skipped without changing their configuration or version. New rows are created with version 1 in one transaction; any other database error rolls the batch back. HTTP 200 returns `{created_count,skipped_count,results:[{id,status:"created"|"skipped",reason?:"already_exists"}]}`. Retrying a committed import safely skips existing entries. All price routes require the administrator domain/session, exact Origin, and POST.
- POST `/api/admin/routing` `{strategy:"least_load"|"highest_balance"|"balanced",tenant_rpm:120,tenant_concurrency:10}`.
- POST `/api/admin/credits` `{tenant_id,amount_micros,reason,idempotency_key}` audited adjustment, positive only.
- Former `/api/billing/checkout`, `/api/admin/refunds`, and `/api/payments/*` routes return 404. No Stripe calls, webhook processing, or online payment capability remains. Historical payment data is retained in the database.
- Native SDK endpoints `/openai/v1/chat/completions`, `/openai/v1/responses`, `/anthropic/v1/messages`, `/anthropic/v1/messages/count_tokens`, and each provider's `/v1/models`. Access Key Bearer (Anthropic also x-api-key). Native traffic must not use cookie auth.
- Anthropic POST `/anthropic/v1/messages` and `/anthropic/v1/messages/count_tokens` accept inline `image` blocks only in a user message's content array or its `tool_result.content` array. Nested tool results are unsupported. The image block allows only `type`, `source`, and optional `cache_control`; the source must contain exactly `{type:"base64",media_type:"image/png"|"image/jpeg",data:string}`. Data must use standard base64 without whitespace or a data-URL prefix. Existing cache checks remain in force, including rejection of one-hour cache writes.
- Images must be complete, decodable static PNG/JPEG files whose format matches the declared media type. The local limits are 20 images per request, 8,000 pixels on either axis, 16,000,000 pixels per image, and 32,000,000 pixels across the request, including tool results. The whole original JSON body, including base64 and text, remains limited to 2 MiB. All limits apply together. APNG, GIF/WebP and other formats, URL sources, uploaded-file references, assistant/system image blocks, and OpenAI image input remain unsupported. Invalid image input is rejected before upstream forwarding or capacity/money reservation.
- Validated image payloads are forwarded without image resizing or recompression and are not written to request logs. Existing model-alias rewriting and output-limit normalization still apply to the request; this is not a byte-for-byte guarantee for the enclosing JSON. Clients should resize/crop or compress before base64 encoding and leave room for its roughly one-third size overhead, JSON, and text.
- The conservative input bound is `2 * (original_body_bytes - validated_image_base64_logical_bytes) + 4096 + sum(2 * ceil(width / 28) * ceil(height / 28) + 256)`. Only validated image positions contribute to the subtraction; similar text/tool arguments do not, and extra JSON-escape bytes remain in the bound. The same input bound feeds reference-price context limits, TPM admission, and monetary reservation together with the output bound. It is not billed usage: settlement uses verified upstream usage and the immutable price snapshot. Explicit `count_tokens` requests have no RelayPine monetary reservation or charge, remain subject to access/context/capacity checks, and cannot stream. The gateway does not automatically invoke `count_tokens` before generation.
- Provider `/v1/models` lists the local published catalog, filtered by protocol, enabled status, client-key model permissions, and a matching enabled endpoint. Upstream key discovery does not publish models. An empty local catalog yields an empty list; model lists do not check wallet balance, credential capacity, or instantaneous upstream availability.
- New requests require usable metered pricing, reserve the RelayPine wallet balance before upstream I/O, and deduct verified usage afterward. Legacy unpriced models are not advertised or callable until priced. Official reference models only route to the provider’s canonical HTTPS API origin (root or `/v1` path); compatible hosts require explicit manual prices. Their reference metadata also bounds input to the priced context tier. All authentication, model permissions, rate/concurrency limits, output bounds, protocol checks, and proxy behavior still apply.
- Request snapshots expose `billing_mode` and `cost_status`. A historical usage-only request has `cost_status=untracked`, even when token usage is known; metered costs are `recorded` or `pending` according to settlement state. These values come from the request's immutable price snapshot, not the model's current configuration. Usage-only requests do not add zero-value entries to the money ledger.
- Anthropic forwards `anthropic-version` (default `2023-06-01`) and the selected credential's nonempty `workspace_id` as `anthropic-workspace-id`. Client workspace headers never override routing configuration. Neither workspace nor beta headers are forwarded to OpenAI upstreams.
- `anthropic-beta` accepts repeated header fields and comma-separated values, trims optional spaces/tabs, deduplicates tokens, and enforces 1024 bytes/16 tokens before deduplication. Supported flags: `task-budgets-2026-03-13`, `thinking-display-updates-2026-08-18`, `thinking-binding-controls-2026-08-01`, `interleaved-thinking-2025-05-14`, `fine-grained-tool-streaming-2025-05-14`. Unknown, malformed, or unsupported beta flags return HTTP 400 before capacity or money reservation and before an upstream call.
- OpenAI standard cache writes are normalized from `input_tokens_details.cache_write_tokens` or `prompt_tokens_details.cache_write_tokens`; ordinary input excludes both cache reads and writes. The 30-minute write rate replaces the ordinary input rate. Anthropic 5-minute writes remain separately priced. Premium 12-hour OpenAI and 1-hour Anthropic writes are rejected; invalid or unsupported usage in a terminal stream never falls back to earlier partial totals.
- Any `fallbacks` property is rejected before reservation. Server-side fallback beta flags are also rejected; each fallback attempt can use a different model and price, which the current single-model accounting does not support. Existing standard-tier, content, tool, caching, and output-limit checks apply to beta requests too.

UI routes: customer origin `/` product entry, `/app` overview, `/app/keys`, `/app/models`, `/app/usage`, and `/app/billing`. Operational routes are available only on the admin origin. Both use the same email-code login flow, without a separate waitlist enrollment flow. No invented traffic or finances; an empty workspace starts with zero credit.

Bootstrap provisions the sole administrator configured by required `SUPERADMIN_EMAIL`
without a password. Missing or invalid email configuration prevents startup.
`BOOTSTRAP_EMAIL` is no longer used. An email match alone never authenticates:
the mailbox OTP must be delivered and verified. Previously waitlisted users gain
a normal workspace only after a successful public-origin email verification.
Existing identities retain their own tenants and balances. Legacy password
credentials, legacy sessions, and keys issued before mailbox verification are
retired; verified customer accounts and their sessions/keys survive startup.
Sessions use `email_otp_customer` or `email_otp_admin` authentication methods;
previous sessions require one new sign-in after this audience-isolation update.
Changing the configured administrator revokes the former operator's sessions
and keys and demotes its role, without transferring its tenant or balance.
No signup bonus, balance grant, online payment, or retroactive charging occurs
as part of sign-in or role migration.

Email delivery uses `MAILGUN_API_KEY`, `MAILGUN_DOMAIN`, `MAILGUN_FROM`, and optional
`MAILGUN_API_BASE` (`https://api.mailgun.net` or `https://api.eu.mailgun.net`). The
existing 32-byte `MASTER_KEY` derives a separate HMAC key for code verification;
Redis stores only a challenge ID and keyed digest, never the plaintext code.
Unconfigured delivery keeps the gateway running but returns an explicit 503.
